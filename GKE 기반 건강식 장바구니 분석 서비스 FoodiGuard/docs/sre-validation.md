## 2. 알림 정책

Cloud Monitoring 에 7종을 등록했다. 조건은 모두 PromQL 이다.

| 정책 | 조건 | 지속 |
|---|---|---|
| API 5xx 오류율 | 5% 초과 | 5분 |
| API p95 지연 | 1초 초과 | 10분 |
| DB p95 지연 | 500 ms 초과 | 10분 |
| API 가용성 | `up == 0` | 3분 |
| 컨테이너 재시작 | 10분 내 발생 | 5분 |
| 원재료 매칭률 하락 | 0.95 미만 | 10분 |
| 영양정보 누락률 상승 | 1% 초과 | 10분 |

**알림 채널은 아직 없다.** 경보는 Cloud Monitoring 에 기록되지만 아무에게도 전달되지
않는다. 운영 전에 수신자를 정해 채널을 붙여야 한다.

## 3. 부하 테스트

클러스터 안에 별도 파드를 띄워 API 서비스를 직접 호출했다(부하 생성기가 API 파드의
CPU 를 갉아먹지 않도록 분리). 동시성 10, 시나리오당 45초.

| 시나리오 | RPS | p50 | p95 | p99 | 오류율 |
|---|---|---|---|---|---|
| 기본 목록 | **106.0** | 91 ms | 117 ms | 166 ms | 0% |
| 키워드 검색 | **3.2** | 3,006 ms | 3,792 ms | 3,948 ms | 0% |
| 알레르기 제외 | **5.1** | 1,595 ms | 3,520 ms | 4,055 ms | 0% |

오류는 한 건도 없었다. 시스템은 죽지 않고 **느려질 뿐이다.**

### 병목은 API 가 아니라 DB 다

부하가 걸린 동안의 자원 사용량:

```
API 파드 CPU      35 m   (0.035 코어)
웹 파드 CPU        1 m
Cloud SQL CPU     91 %   ← 여기
```

API 는 거의 놀고 있다. **DB 의 1 vCPU 가 한계**이므로 API 복제본을 늘려도 처리량은
늘지 않는다. 같은 시각 DB 쪽 p95 는 이렇게 밀렸다.

| operation | p95 |
|---|---|
| `product_search_count` | 3,668 ms |
| `product_search_list` | 3,294 ms |
| `data_quality` | 2,425 ms |

### 경로 간 격차가 33배다

기본 목록 106 RPS 대 키워드 검색 3.2 RPS. 같은 테이블인데 이렇게 벌어지는 이유는
**기본 목록만 부분 인덱스를 타기 때문**이다(`docs/performance.md` 참조). 키워드
검색(`ILIKE %...%`)과 알레르기 제외는 여전히 전수 스캔이다.

### 부하가 헬스체크를 밀어낸다

부하 중 `/api/health/ready` 의 p95 가 **2,205 ms** 였다. 검색이 DB 커넥션을 다 물고
있어서다. 준비성 프로브가 이 지연을 넘기면 파드가 트래픽에서 빠지고, 남은 파드로
부하가 몰려 같은 일이 반복될 수 있다. 복제본이 1개라 특히 그렇다.

## 4. 통제된 장애 실험

API 파드를 삭제하고, 외부 진입점(`http://<EXTERNAL_IP>/api/health/live`)을 0.5초 간격으로
호출하며 복구를 측정했다.

| 시각 | 사건 |
|---|---|
| 21:54:02 | `kubectl delete pod` 실행 |
| 21:54:03 ~ 21:54:06 | **502 연속 4회 — 완전 실패 구간** |
| 21:54:03 | 새 파드 생성, 이미지 pull 517 ms |
| 21:54:27 ~ 21:56:24 | 산발적 타임아웃 8회 |
| 이후 | 정상 (외부 200, 20 ms) |

폴링 240회 중 성공 228회(95%), 실패 12회(5%).

**확실한 정지 구간은 약 4초**다. 그 뒤의 산발적 타임아웃은 nginx 가 사라진 파드
주소로 맺어둔 연결을 정리하는 동안 발생한 것으로 보인다.

### 이 실험이 드러낸 것

**자동 복구는 동작한다.** 쿠버네티스가 파드를 즉시 재생성했고 사람 개입 없이 돌아왔다.

**그러나 이 장애로는 경보가 울리지 않는다.** API 가용성 정책의 지속 조건이 3분인데
실제 정지는 4초였다. 자기 치유가 경보보다 빠르다. 이 정책은 파드 한 개가 죽는
상황이 아니라 **지속되는 장애**를 잡는 용도로 이해해야 한다.

짧은 정지도 잡고 싶다면 별도의 외부 업타임 체크가 필요하다. 다만 4초짜리 정지마다
사람을 깨우는 것이 옳은지는 따로 판단할 문제다.

**복제본이 1개인 것이 4초의 원인이다.** 2개였다면 나머지 하나가 트래픽을 받아
무중단이었을 것이다.

## 5. 남은 권고

측정으로 뒷받침되는 순서대로 적는다.

1. **키워드 검색 · 알레르기 제외 경로 최적화** — 33배 격차가 가장 큰 문제다. DB 증설보다
   먼저 할 일이다. 증설은 비용이 계속 들지만 인덱스는 한 번 고치면 끝난다.
2. **API 복제본 2개 이상 + PDB** — 장애 실험의 4초 정지를 없앤다.
3. **알림 채널 연결** — 지금은 경보가 아무에게도 가지 않는다.
4. **HPA** — 단, DB 가 병목이므로 API 만 늘리면 효과가 없다. 1번 뒤에 판단한다.

## 6. 재현 방법

```bash
gcloud container clusters get-credentials foodiguard-cluster \
  --region asia-northeast3 --project example-gcp-project

# 알림 정책
gcloud monitoring dashboards list --project=example-gcp-project

# 부하 테스트: 별도 파드에서 서비스 직접 호출
kubectl run loadgen --image=<backend image> --restart=Never --command -- sleep 3600
kubectl cp loadtest.js loadgen:/tmp/loadtest.js
kubectl exec loadgen -- env CONCURRENCY=10 SECONDS=45 node /tmp/loadtest.js

# 자원 사용량
kubectl top pod
```

데이터 품질과 지연은 `docs/observability.md` 5절의 PromQL 로 같은 값을 본다.
